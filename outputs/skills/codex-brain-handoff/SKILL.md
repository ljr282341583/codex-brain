# Codex 独立大脑接力

只使用 Codex 独立记忆库保存中文项目摘要。已有开发流程仍决定需求、设计、实现和验收门禁，本技能不代替这些流程。用户在当前 Codex 开发项目实际下达“收尾／Codex 大脑收尾”，表示执行下述自动建档、提交、必要时建私有仓库及推送项目和大脑的流程，无须再次索要这些动作的常规确认。“保存进度”默认只保存本地；讨论或引用触发词、没有明确项目的普通聊天不触发上传。用户当次限定“只保存本地／不要上传”等范围时优先服从。

## 定位与隔离

1. 读取当前 Codex home 下的 `brain-config.json`：优先使用已设置的 `CODEX_HOME`，否则使用用户目录 `.codex`。配置必须有 `owner: "codex"`、`repository_root`、`notes_root`、`templates_root` 和 `project_bindings`。
2. 校验笔记和模板路径解析后确实位于本配置的仓库根下，且不与 `protected_roots` 中任一路径重叠；不得通过目录链接绕入受保护位置。配置不存在、路径冲突或归属不明时报告问题，不探测或改写 DSH 配置来凑一个可用入口。
3. 不读取 `.agent-brain` 来定位本库，不调用共享 `session-handoff`，不修改 `.dsh`、共享 `.agents/skills/session-handoff` 或原 `agent-brain`。用户明确要求跨工具接手时，单独确定范围。
4. 普通问答不建档，不导入旧 DSH 项目，不把本技能安装验收样本当真实项目。配置和规则维护讨论不自动变成业务项目收尾。

## 定位当前项目

从本次明确操作的项目路径出发，有 Git 时用 `git -C <路径> rev-parse --show-toplevel` 找仓库根，并读取完整 origin 身份；无 Git 时用用户明确指定的项目根。不要把聊天所在的通用工作区、`app`、`outputs`、`work` 或工作树随机目录名直接当项目 ID。

如果 Git 根是包含多个项目的上层目录，不能把整个上层仓库按当前项目上传，先明确范围。当前项目本身就是配置中的大脑仓库时，只对同一个仓库执行一次提交／推送，不重复建仓或嵌套复制。

先匹配配置 `project_bindings` 中经解析的本机 `code_root`，再核对已知完整远程身份。远程身份比较需兼容同一仓库的 SSH/HTTPS 写法并去掉 `.git`，不能只比 URL 末段。同仓库不同工作树共用项目档案，但记录当前分支与工作树位置。找不到精确映射或发现同名不同仓库时先核对，不猜测归属。

新项目采用用户已给定的名称或会话中已明确的项目名作为 `project_id`，不要求用户另说“建立大脑档案”。必须是单层合法目录名，禁止路径分隔符、`..`、绝对路径和 Windows 保留设备名；解析后的档案目录须仍在 `notes_root` 内。明确真实项目根和目标后即用模板建立 `CONTEXT.md`、`NEXT.md`、`DECISIONS.md` 和 `JOURNAL/`；收尾时再检查一次，漏建则先补建，并在本机 `project_bindings` 追加：

```json
{"project_id":"项目名称","code_root":"本机实际项目根目录","canonical_remote":null}
```

远程存在时填写归一化的完整仓库身份；绑定不包含密钥或带凭据 URL。没有确定的项目目标时不提前建档。保留配置其他字段，不覆盖其他项目绑定。

## 开工与恢复

- 先读该项目 CONTEXT 和 NEXT；DECISIONS 按任务检索，JOURNAL 仅追溯时读取。
- 与当前文件、分支、HEAD、未提交修改和必要的真实验证核对。区分“笔记曾记载”和“本次已证实”；不把以前测试通过当作现在已通过。
- 有冲突时说明差异；代码证明实现状态，用户确认的决定证明意图，不能单凭某一份旧笔记覆盖另一方。
- 没有档案时自动建立最小档案；关键决定获确认或阶段结束时保存本地摘要，减少全靠最后一次聊天恢复的风险。这些本地检查点不触发提交和上传，也不跳过阶段门禁。禁止从 DSH 同名目录自动接管。

## 保存进度与收尾

1. 先确保当前项目档案存在，缺失即自动补建。只采集真实可追溯的产出、用户确认、代码状态、实际验证、未完成项和下一步；早期上下文已缺失则说明缺失，不编造历史。日期时间使用 Asia/Shanghai，附机器名与 Codex 来源。
2. 新建 `JOURNAL/YYYY-MM-DD-HHmmss-Codex.md`；同名存在则追加或使用新后缀，不覆盖历史。短记结论与理由，不搬运对话、大段代码、凭据或敏感配置。
3. 更新 NEXT 的当前状态、可执行下一步、阻塞和验证边界；旧条目先移入 JOURNAL。CONTEXT 只更新已确认的稳定事实，DECISIONS 只追加已确认决定。旧决定被推翻时保留正文并标明取代关系。
4. 先保存本地笔记。“保存进度”或用户明确限定只本地时，到此结束并说明尚未云端同步。实际“收尾”继续执行下面的 GitHub 同步，不再询问是否建档、提交、建私有仓或推送。
5. 检查项目完整工作区和本次候选文件。无 Git 时只在已确认的项目根初始化仓库，保留已有 `.gitignore`，补充适用的 `work/`、依赖／缓存、`.env` 和凭据排除项。逐项核对源代码与必要资源，排除密钥、令牌、账号快照、私钥、个人数据、构建缓存和无关大文件；已跟踪文件不能仅靠 `.gitignore` 排除。对拟推送的历史也检查凭据风险，不能只检查最新工作区。可安全排除的新文件自动排除；疑似秘密已在跟踪内容／历史中、项目边界不明或存在无法区分归属的改动时先说明具体阻塞，不上传存疑内容。只暂存本项目此次明确文件，不用无范围 `git add -A`。
6. 按当前项目既定要求验证，先提交项目代码，再重新读取最终 HEAD，更新笔记后提交大脑。基线和最终提交分开记录；没有变动就跳过空提交。未通过验收的工作可按 WIP 保存，但说明失败和未验证部分，不声称可发布；本流程不包含 Release、部署、发包或改变已有仓库可见性。
7. 对项目仓库和独立大脑分别同步：读取配置 `handoff.github_owner` 并用 `gh api user --jq .login` 核对当前账号。账号不一致或登录失败则保留本地，报告所需操作，不更改登录身份。已有 origin 时核对完整项目身份、远程可见性和写权限，确认没有超出授权的改动／待推送提交后复用；公开仓库不因收尾被改为私有，若其内容是否适合公开不明确则询问。没有 origin 时，项目使用稳定 ASCII 仓库名并写回绑定 `github_repository`；中文名无法直接作仓库名时从用途取简短英文名。大脑固定使用配置 `handoff.brain_repository`。检查同名仓库是否存在，不能把无 origin 的本地目录静默绑定到已有同名远程；存在撞名则选不冲突的新名称并记入绑定，归属仍不明确则询问。新仓库明确使用 `--private`；可按 `gh repo create OWNER/REPO --private --source <项目根> --remote origin` 创建，再推送当前明确分支，不镜像所有分支，不推无关历史。
8. 项目推送后用远端分支 SHA 核对本地最终 HEAD；把项目同步结果写入本次 JOURNAL，再提交、推送大脑并核对其分支 SHA。大脑远程为独立 `codex-brain`，不使用原 DSH `agent-brain`。失败保留本地档案与提交，不自动 pull/rebase、强推、重置或改写历史；禁止把部分成功说成全部成功。先检查远端实际状态再重试，防止网络结果不明时重复建仓。
9. 回读修改内容，核对占位符、路径和证据。分别汇报项目与大脑的仓库链接、可见性、分支、最终提交和同步结果，给出下一次接手动作；本次大脑提交哈希在最终汇报中给出，不在包含它自身的笔记中要求记录该同一提交哈希。构建与打包按当前项目明确约定执行，不套用 DSH 项目特例。

删除电脑文件前仍须获得用户允许。已有未完成改动保持原样。
